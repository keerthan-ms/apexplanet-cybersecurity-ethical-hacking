## Brute force methodology

Brute force (and its smarter siblings) tries candidate credentials until one
works. It is noisy, it is slow against anything properly configured, and it is
still the first thing real attackers run against an exposed service because
most environments are not properly configured.

### Hydra command structure

```text
hydra [login options] [password options] [service://target] [service options]

Login options
  -l USER          single username
  -L FILE          username list, one per line
  -C USER:PASS     colon-separated credential pair(s) — stop splitting the lists

Password options
  -p PASS          single password
  -P FILE          password list
  -x MIN:MAX:CHARS pattern brute force instead of a wordlist, e.g. -x 4:4:a
                   (length MIN:MAX, charset: a=lower, A=upper, 1=digits, special)
  -e nsr           extra guesses: n = try the null/empty password,
                   s = try the username as password, r = reverse the username

General behaviour
  -s PORT          non-default port
  -t TASKS         parallel connections (default 16; drop to 1-4 for SSH)
  -f               stop on first valid credential (use with a small wordlist
                   when you only need one entry point)
  -F               opposite of -f: stop when all passwords for a user are tried
  -V / -v          verbose: log every attempt (-V shows attempts, useful with -f)
  -o FILE          write results to a file
  -b FORMAT        output format: text (default), json, jsonv, or ivverbose
  -w TIMEOUT       wait time for responses
  -c TIME          minimum time between connection attempts to the same host
  -I FILE          ignore addresses in FILE (don't brute hosts that are down)
  -m MODULE        module-specific options (each hydra -U <module> explains)
  -x HELP          pattern-brute help
```

### Real usage patterns

SSH — single user, wordlist, slow, stop at first hit:

```bash
hydra -l msfadmin -P /usr/share/wordlists/rockyou.txt \
      -t 1 -f -V \
      ssh://192.168.56.10
```

Why `-t 1`: SSH drops connections after a few parallel authentication
attempts, and the OpenSSH `MaxStartups` throttling makes parallelism a
self-defeating noise source. Parallelism belongs on services designed for it.

SSH — multiple users, targeted password list, JSON output for the report:

```bash
hydra -L users.txt -P passwords.txt \
      -t 4 -f -o hydra-ssh.json -b json \
      ssh://192.168.56.10
```

HTTP login form (POST). Hydra's `http-post-form` takes
`path:data:fail-condition` where `^USER^` and `^PASS^` are substituted, and
the fail condition is a string that appears **only on failure**:

```bash
hydra -l admin -P passwords.txt \
      -t 4 -f -V \
      192.168.56.10 http-post-form \
      "/login.php:username=^USER^&password=^PASS^:F=Invalid credentials"
```

Find the failure string by logging in with a deliberately wrong password once
and reading the response (or the page source) — do not guess it. Add
`-c 1` if the app rate-limits, and check the app's own lockout behaviour
before you start.

HTTP basic auth:

```bash
hydra -L users.txt -P passwords.txt -f \
      http-get://192.168.56.10/admin/
```

FTP (banner and return codes differ; `-e s` also tries the username as the
password — Metasploitable2's own services make that a useful first guess):

```bash
hydra -l ftpuser -P passwords.txt -e s -f -V \
      ftp://192.168.56.10
```

Pattern brute force when you suspect a short PIN or a year-suffixed password
instead of a wordlist:

```bash
hydra -l root -x 4:4:1 ssh://192.168.56.10   # four digits, 0000-9999
```

### How to think about rate

Three separate limits decide how fast you can go, and only one of them is
yours:

1. **The tool** — `-t` and `-c`.
2. **The service** — SSH's `MaxAuthTries` (default 6 per connection) and
   `MaxStartups` (default `10:30:100` — start dropping connections when 10
   concurrent unauthenticated sessions exist), Tomcat/JBoss request queues,
   HTTP connection pools.
3. **The defence** — account lockout and rate limiting, which is where this
   becomes an ethical question as well as a technical one.

**Account lockout policy is the defender's control, and it is the reason
reckless brute force is harmful.** A typical policy locks an account after 5–10
failed attempts for 15–30 minutes. Running `-t 16` against a single username
will lock that account almost immediately, which:

- denies service to the legitimate user (a denial of service caused by *your*
  test),
- may trigger an incident ticket and an investigation about an attack that
  was you,
- and tells an attacker nothing they could not have got with `-t 1` and
  patience.

Safe operating practice for authorised testing:

- Agree the rate and the target accounts with the client **in writing**, and
  use dedicated test accounts, never production user accounts.
- Start slow (`-t 1` for SSH, `-t 4` for HTTP forms), watch the service, and
  only increase within the agreed limit.
- Use `-f` so you stop at the first valid credential and do not keep hammering
  an account that already worked.
- Prefer a small, *targeted* list over rockyou.txt against a production
  endpoint. "Top 100 passwords we have seen in our own breach corpus" both
  finds more and annoys less.
- Stop the run if lockout warnings appear in the client's logs. Record the
  observation; it is a finding ("lockout threshold 5, no rate limiting by
  source IP").

## Password cracking methodology

Brute force attacks a *service*; cracking attacks a *hash*. The hashes come
from somewhere: a dumped SAM (see
[`02-exploitation-with-metasploit.md`](02-exploitation-with-metasploit.md)),
a stolen `/etc/shadow`, a database breach, an application's password table,
a Kerberoasted service ticket, a NetNTLMv2 capture. Cracking is offline — no
lockouts, no rate limits imposed by the defender, only your own compute.

### Identifying the hash type

Identification is a lookup on the format. Prefixes are the giveaway for
crypt strings; hex length and context are the giveaway for raw digests.

| Looks like | Likely type | Notes |
|---|---|---|
| `$2a$…`, `$2b$…`, `$2y$…` | **bcrypt** | OpenBSD/John/PHP variants; next field is the cost factor, e.g. `$2b$12$` |
| `$6$…` | **sha512crypt** | glibc default for years |
| `$5$…` | **sha256crypt** | |
| `$1$…` | **MD5crypt** | FreeBSD/glibc legacy |
| `$y$…` | **yescrypt** | Modern Debian/Ubuntu/Kali default |
| `$apr1$…` | Apache MD5 | `.htpasswd` files |
| `$pbkdf2-sha256$…`, `pbkdf2_sha256$260000$…` | PBKDF2 | Python/Django/Rails apps |
| 32 hex chars, no salt | **NTLM** | `MD4(UTF-16LE(password))`; Windows SAM |
| 32 hex chars, no salt | **MD5** | Bare |
| 40 hex chars | **SHA-1** | Bare |
| 64 hex chars | **SHA-256** | Bare |
| `$krb5tgs$23$…` | Kerberoastable service ticket | Crack the SPN password offline |
| `$krb5asrep$23$…` | AS-REP roastable account | No pre-auth required |
| `user::domain:LM:NTLM:challenge` | NetNTLMv1/v2 capture | v2 resists offline cracking to plaintext; relay is the real risk |
| `hash:salt` or `salt:hash` pair | Raw hash + separate salt | Order varies by system; check the app's code |

Confirm with the tool rather than guessing — both John and hashcat will tell
you when the format is wrong:

```bash
john --list=formats | tr ',' '\n' | grep -i bcrypt   # does this John support it?
john --format=bcrypt --show hashes.txt               # identification attempt
hashcat -m 3200 --example-hashes | head              # show the exact bcrypt format
```

Common hashcat mode numbers: `-m 0` MD5, `-m 100` SHA-1, `-m 1400` SHA-256,
`-m 1000` NTLM, `-m 1800` sha512crypt, `-m 3200` bcrypt, `-m 13200` PBKDF2-HMAC-SHA512,
`-m 19600` Kerberos TGS-REP, `-m 18200` Kerberos AS-REP.

### Wordlists, and where they come from

| Wordlist | Origin | Use |
|---|---|---|
| `rockyou.txt` | The 2009 MySpace breach (14,344,391 passwords), shipped zipped in Kali at `/usr/share/wordlists/rockyou.txt.gz` | The canonical first run — it is what most "was the password in a wordlist" questions mean |
| SecLists (`/usr/share/seclists/Passwords`) | Community-maintained collection (Daniel Miessler et al.) | Targeted subsets: `Common-Credentials`, `DarkStar27-Usernames`, `Default-Credentials`, per-application lists |
| CrackStation wordlist | Built from multiple public breaches, de-duplicated | Larger than rockyou; good second pass |
| Hashcat `example.dict` + rules | Shipped with hashcat | Quick sanity check |
| Your own corpus | Passwords seen in *your* organisation's breaches, policy defaults, seasonal patterns, product names | The most effective list you will ever build, because it is about this organisation |

**Rules (mutation) beat bigger lists.** Rules append, prepend, capitalise and
substitute — turning `summer` into `Summer2026!`, `sUmm3r`, `summer!`, and so
on. A 10k-word list plus rules routinely outperforms a 10M-word list without
them.

```bash
# John: jumbo build's rules (best64 is the highest-yield default)
john --wordlist=rockyou.txt --rules=best64 hashes.txt
john --rules --wordlist=mycorp-dict.txt hashes.txt   # built-in rule set

# hashcat: rule files
hashcat -m 1000 -a 0 hashes.txt rockyou.txt -r /usr/share/hashcat/rules/best64.rule
hashcat -m 3200 -a 0 bcrypt-hashes.txt mycorp-dict.txt -r dive.rule
```

### Wordlist vs brute force vs mask attack

| Approach | Keyspace covered | Best for | Wastes compute when… |
|---|---|---|---|
| **Wordlist** | Whatever is in the list | Anything built from human choices — which is almost everything | The password was not generated by a human, or is longer/more random than the list |
| **Wordlist + rules** | The list, multiplied by rule transformations | Human passwords with patterns (`Name2024!`) | The rule set does not model the mutation used |
| **Incremental / brute force** | Exhaustive over a charset+length | Very short passwords; final fallback | Anything above ~7–8 mixed characters on CPU |
| **Mask attack** (`-a 3`) | Structured guess: `?l?l?l?l?d?d?d?d` = 4 lowercase + 4 digits | When you know the policy ("8 chars, ends with 4 digits", "surname + year") | Your model of the password is wrong |

```bash
# mask attack encoding: ?l lower, ?u upper, ?d digit, ?s special, ?a all
hashcat -m 3200 -a 3 bcrypt.txt "?u?l?l?l?l?l?d?d?d?d!"   # "Kbxcd1234!"
# or with a jump: first char any of [KAP], etc.
john --incremental=Lower --min-length=1 --max-length=8 hashes.txt
```

### GPU vs CPU

- **CPU (John, hashcat's CPU backends):** good for bcrypt/sha512crypt
  (thousands of guesses per second), which are deliberately slow *per guess*.
  Convenient: no driver setup, runs anywhere.
- **GPU (hashcat):** hundreds to thousands of cores. Dominates on cheap
  hashes — MD5, NTLM, SHA-1/256 — with throughput in the billions of
  guesses per second on a multi-GPU rig. Even bcrypt, designed to be slow,
  becomes thousands to tens of thousands of guesses per second per GPU
  (see the arithmetic below).
- **Consequence for defence:** an unsalted fast hash is effectively plaintext
  at GPU speeds; a cost-12 bcrypt is still years for a full keyspace. The
  algorithm choice matters more than the attacker's hardware.

## Why modern hashing changes the economics

The goal of a password hash is to make the *defender's* one-time verification
cheap and the *attacker's* offline search expensive. Modern password hashes do
this three ways: a **slow algorithm** (or explicit iteration count), a
**per-password salt**, and where appropriate **memory hardness**.

**Bcrypt's cost factor.** Bcrypt is the Blowfish-based key schedule run
`2^N` times, where `N` is the stored cost. A `$2b$12$` hash means
2^12 = **4096 iterations**. Raising the cost by one doubles the work for both
attacker and defender; the defender pays it once per login, the attacker pays
it for every guess forever.

**The salt's job.** A unique random salt per password means each hash must be
attacked separately. Rainbow tables and precomputation are useless; the same
password in two accounts produces two unrelated hashes.

### Worked estimate

Assume an 8-character lowercase password: keyspace
26^8 = **208,827,064,576 ≈ 2.09 × 10^11** candidates (average half that to hit
one: ~1.04 × 10^11).

| Scenario | Guesses/sec | Time for full keyspace | Arithmetic |
|---|---|---|---|
| **Unsalted MD5, GPU rig** | 100 billion (1 × 10^11) | **~2.1 seconds** | 2.09 × 10^11 ÷ 10^11 = 2.09 s |
| **bcrypt cost 12, one CPU core** | 100 | **~662 years** | 2.09 × 10^11 ÷ 100 = 2.09 × 10^9 s; ÷ 3.1536 × 10^6 s/yr = 662 yr |
| **bcrypt cost 12, one GPU** | 10,000 | **~6.6 years** | 2.09 × 10^11 ÷ 10^4 = 2.09 × 10^7 s; ÷ 3.1536 × 10^6 = 6.62 yr |
| **sha512crypt ($6$), CPU core** | ~1,000 (round number) | **~6.6 years** | 2.09 × 10^8 s ≈ 6.6 yr |

Same password, same attacker, four orders of magnitude apart — that is the
entire argument for modern password hashing in one table. (These are round
numbers for reasoning, not benchmarks; measure on your own hardware.)

**And the counter-move on defence — length.** The keyspace grows
exponentially with length, while human effort grows only linearly. A
five-word Diceware passphrase drawn from a 7776-word list:

```
keyspace = 7776^5 = 2.84 × 10^19
at 10,000 guesses/sec (bcrypt-12 GPU): 2.84 × 10^15 s ÷ 3.1536 × 10^6 s/yr
                                      ≈ 900,000,000 years
```

Nine hundred million years versus six and a half years, for a password that is
easier to type and remember than `Tr0ub4dor&3`. Complexity rules pushed users
toward short, patterned, reused passwords; length pushes them toward the
property that actually costs the attacker the most.

## Defences

**Password policy — the current position**

- **Length over composition.** Require at least 8 characters for user-chosen
  passwords and 64 or more where the user chooses a passphrase; *allow* all
  printable characters including spaces. Arbitrary composition rules ("one
  upper, one digit, one symbol") are known to push users into `Password1!`
  patterns that appear in every cracker's default lists.
- **Screen against known-bad.** Check candidate passwords against breached
  corpora (e.g. the k-anonymity range API of a public breach corpus) and
  against your own list of organisational patterns (product names, seasons,
  `Company2026!`). This is more effective than any composition rule.
- **Stop routine expiry.** The widely cited modern position (NIST SP 800-63B
  in the US, and the UK NCSC's password guidance) is that **periodic
  password changes are no longer a primary control**: users rotate by the
  minimum, which degrades rather than improves the password, and the real
  risk is compromise, not age. Rotation remains appropriate on evidence of
  compromise, when an account is shared or role-based, or for high-privilege
  accounts under stricter policy. Verify the current edition of the guidance
  before you write it into a policy document — the specific recommendations
  have changed before and will again.
- **Never store reversible or fast-hashed passwords.** Use bcrypt/scrypt/
  Argon2id/PBKDF2 with a per-user salt and a modern cost factor. NTLM
  "hashing" is not hashing in this sense at all.
- **Disable LM and NTLMv1**, and move toward blocking NTLM entirely
  (see [`02-exploitation-with-metasploit.md`](02-exploitation-with-metasploit.md)
  for the controls).

**Multi-factor authentication.** The single highest-value control: a cracked
or phished password is then not sufficient. Prefer phishing-resistant factors
(FIDO2/WebAuthn security keys, certificate-based auth) over SMS one-time
codes, which are relayable.

**Password managers.** They solve the real constraint — nobody can remember
100 unique passwords — so uniqueness becomes possible for humans. Organisation
ally, an enterprise vault also gives you an inventory of shared credentials,
which is its own security win.

**Rate limiting and lockout.** Both, and they are not the same thing:

- **Account lockout** (5–10 failures, 15–30 minutes) stops targeted guessing
  but is itself a denial-of-service vector — an attacker can lock out a known
  account deliberately. Prefer thresholds that allow a human a couple of
  mistakes.
- **Per-source rate limiting** (exponential backoff, CAPTCHA, connection
  throttling) stops distributed guessing far more effectively than lockout,
  and cannot be weaponised against the user.
- **Alerting** on authentication-failure bursts, by source and by target
  account, catches both the attacker and your own misconfigured service.

**Credential-stuffing defence.** Users reuse passwords, so a breach of
someone else's site becomes an attack on yours. Unique passwords per site
(via a manager), breach-corpus screening at registration, and MFA are the
three layers that work.
